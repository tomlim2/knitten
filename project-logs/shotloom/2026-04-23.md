# shotloom — 2026-04-23

## ADR-0029 정규화 레이어 설계 — 초안에서 최종안까지

### 배경

- `shotloom-retarget` 가 정규화 로직까지 떠안고 있었음 (`adapters::arp_vrm::align_full_body_rest`, `vrm_rest`, foot contact 등이 retarget math 와 같은 크레이트에 섞임)
- Multi-source 로드맵 (VRM 오늘 / FBX / PMX) — post-import 은 source-agnostic 해야 함
- A-pose 전환이 미래 예정. 전환을 어떻게 구조로 대비할지가 관건
- shotloom 은 편집툴. face / body 양쪽 채널 편집, TTS 향후 합류 고려 필요

### 이력 (방향 전환 3회)

**1. 초기 안**: canonical rest pose enum (`CinevArpV1`, `APoseV1`) + `ACTIVE_CANONICAL_POSE` const + 캐시 키 태그

→ 리뷰 결과 **거절**. A-pose 수학 명세가 없는 상태에서 enum 두 번째 variant 는 dead code. 광고하는 미래 shape 은 premature abstraction.

**2. 방향 전환**: enum/태그 전부 드롭. `normalizer crate 분리만` 을 핵심으로 축소

**3. 진입점 재설계**: `CharacterModel` 안에 `rest_pose: Option<RestPose>` 필드 내장. source 포맷 지식 소거. `#[serde(skip)]` 로 디스크 스키마 호환

**4. Character-neutral contract 명시**: NormalizedAnimation 이 character-agnostic. 한 번 정규화, 여러 캐릭터 재사용

**5. Type ownership open question**: `NormalizedAnimation` 이 core / per-normalizer / 별도 types crate 중 어디에 사는지는 결정 보류. Leading: `shotloom-core`

**6. Scope creep 한 번**: Track/Clip cross-link 추가했다가 제목 밖이라 revert

### 핵심 결정 (최종안)

| | 결정 |
|---|---|
| 새 crate 2개 | `shotloom-character-normalizer`, `shotloom-animation-normalizer` |
| CharacterModel 확장 | `rest_pose: Option<RestPose>` (serde-skip) |
| 타입 위치 | `RestPose` 는 `shotloom-core`. `NormalizedAnimation` 은 open question (leading: core) |

### Rejected alternatives (5)

- **A** retarget crate 에 정규화 유지 → 덤프 그라운드화
- **B** CanonicalPoseId enum 지금 도입 → premature, dead variant
- **C** 단일 shotloom-normalize crate → character/animation 변경주기 disjoint, 격리 가치
- **D** rest_pose 를 serde persist → outliner/inspector 가 shape 변화에 커플
- **E** RestPose 를 CharacterModel 옆에 별도 pass → caller 마다 pair 수동 운반 부담

### 러닝

- **ADR 수정 자유도는 status 에 달림** — Proposed 단계라 마지막까지 편하게 다듬었음. Accepted 뒤였으면 supersede ADR 필요
- **"Earn the abstraction now, 근데 데이터 모델 부분만큼은 아님"** — 구조(crate 분리, 타입 계약) 는 미래 대비해서 미리 잡되, 런타임 태그 / 버전 enum 같은 데이터 모델은 실제 필요할 때까지 미룸. ADR-0029 가 이 균형 찾는 데 시간 씀
- **타이틀이 scope 의 gate** — Track/Clip cross-link 가 의미적으로 자연스러워도 제목이 "Normalizer Crate Layer for Import" 면 downstream 편집 얘기는 빠지는 게 맞음. ADR 이 scope 커지면 리뷰어가 못 읽음
- **Character-neutral contract 은 편집기 관점에서 배당 받음** — 편집 UI 설계(트랙, 오버라이드) 얘기 나오면서 "한 anim 을 여러 캐릭터에 재사용" 이 실전 가치로 drop. 그래서 ADR 본문에 1급으로 박힘
- **TTS 아직 stub** — stub 을 현재 동작 consumer 인 것처럼 가정하고 ADR 초안 작성했다가 정정. 향후 실제 있는 것 vs 계획만 있는 것 분별 필요
- **"Character-neutral" 원칙이 편집툴 아키텍처 전체를 리드** — NormalizedAnimation 이 신뢰할 만한 canonical 이면 그 위에 레이어링 / 오버라이드 / TTS 합류 / AI 생성 합류 전부 자연스럽게 정리됨

### 아키텍처 Q&A 정리

ADR-0029 설계 과정에서 나온 구조 이해 질문들 — 나중에 구현할 때 기준 삼을 것.

#### 1. Retargeter 의 소속과 역할

- **소속**: animation pipeline. Character pipeline 이 아님. CharacterModel 은 참조용, 수정 안 됨.
- **입력**: `CharacterModel`(rest_pose populated) + `NormalizedBodyAnimation`.
- **출력**: `TargetAnimation` — 이 캐릭터 본별 쿼터니언 트랙.
- **Face 는 retargeter 경로 아님** — 별도 face binding (ARKit 52 → VRM blendshape 이름 매핑) 경로. 수학 없음.

#### 2. Normalizer vs Retargeter 역할 분리

- **Normalizer**: 소스 포맷 → canonical 공간 (파일 파싱, 이름 매핑, 좌표 변환, 테이블 룩업 등 "번역")
- **Retargeter**: canonical anim → 이 캐릭터의 구체 스켈레톤 (쿼터니언 delta 수학 "맞추기")
- Before ADR-0029: 한 crate 가 둘 다 떠안아서 책임 혼탁
- After: 성격 다른 두 작업을 crate 경계로 분리

#### 3. Retargeter = 수식 / pure function

```
output[i][f] = anim[i][f] * bind_delta[i]
bind_delta[i] = character_rest[i]⁻¹ * canonical_rest[i]
```

- **결정론적** → 같은 입력 = 같은 출력. 캐시 가능.
- **역함수 존재 가능** → target → canonical 복원 가능. Re-retarget (다른 캐릭터로) 가능.
- **골든 테스트 가능** → STL-127 Step 0 의 bit-exact regression test 가 이래서 성립.
- **AI 개입 여지 없음** → AI 는 canonical anim 을 **만드는** 단계에만 낄 수 있음.

#### 4. 자동 조정 / 안 하는 조정

Retargeter 가 **자동 조정**: bind pose 미세 각도 차, 본 축 방향 차이, 루트 높이 offset, (본 길이 차이는 로컬 회전이라 자동 반영)

Retargeter 가 **안 하는 조정**: 키 자체 스케일링 (캐릭터 고유 특성 유지), foot ground contact (character normalizer 의 `foot_contact` 가 담당), IK target 조정, timing / style 변경

**중요**: "키 차이" 는 맞추는 게 아니라 **있는 그대로 반영**. 작은 캐릭터와 큰 캐릭터가 같은 canonical gesture 를 받으면 **같은 모양**이되 **공간적 도달점은 다름** — 이게 올바른 동작. 동일 공간 지점 터치가 필요하면 IK 문제.

#### 5. 정규화된 character output 구조

`RestPose` 에 담기는 것:

- **Bone hierarchy** (parent-child)
- **Per-bone rest transforms** (local rotation + translation)
- **Canonical ↔ source 본 이름 매핑** (e.g. `spine_01` ↔ `J_Bip_C_Spine`)
- **Coord convention** (canonical 공간 규약 — Y-up right-handed meters)
- **캐릭터 파생 데이터**: foot_contact, sole_offset, height 등

Normalizer 가 이걸 한 번 생산하면 retargeter 가 매 재생마다 소비.

#### 6. 좌표계는 이미 ADR-0009 로 확정

- **Y-up, right-handed, meters**
- Forward = **-Z** (glTF / Bevy / VRM 관례)
- Blender (Z-up, -Y forward) 소스는 character-normalizer 에서 변환
- CINEVStudio/UE (Z-up, cm) 는 shotloom-s2m 에서 이미 축 교환 + cm→m

ADR-0029 는 이 규약 전제로 작동. 추가 결정 불필요.

#### 7. T-pose vs A-pose canonical 선택

현재 CR pose (임시 canonical) → 미래 A-pose 이행 예정. A-pose 가 선택된 이유:

- 편집툴 성격상 blend / crossfade 품질이 중요 → A-pose 가 자연 rest 에 가까워 artifact 최소
- ARP 소스와 친화 (변환 최소)
- 산업 트렌드 (UE5 Mannequin, MetaHuman, Audio2Face 등이 A-pose)
- AI 생성 모델의 학술 표준 (FLAME 등) 이 A-pose 수렴

**A-pose 안에서도 variant 존재**:

- Flat A-pose (손 편 상태, ARP/VRoid/전통적)
- MetaHuman A-pose (손 살짝 굽힘, 자연 이완 — mocap 쪽 편향)

추천: **Flat A-pose canonical + MetaHuman 소스는 import 시 bind correction**. VRM 타겟이 flat 편향이라 export 깔끔. MetaHuman 은 강력한 소스지만 exchange format 관점에선 특수 케이스.

이건 ADR-0029 scope 밖 — A-pose 마이그레이션 follow-up ADR 에서 명시 결정 필요. 이 대화가 그때 참고 자료.

#### 8. 편집기 UI 는 canonical 공간에서 작동

- Timeline UI 채널 이름 = canonical bone / ARKit 52 channel (소스 본 이름 X, VRM 본 이름 X)
- 편집 = canonical 공간에서 값 조작 (normalize 재실행 불필요)
- Retarget 은 매 재생 / 매 미리보기 프레임에서 재실행 (cheap per-character)
- 시각적 피드백 공간 = 리타게된 캐릭터 (Xiao 나 Ghost) — 보는 화면
- 저장 공간 = canonical 값 (character-neutral)

#### 9. NormalizedAnimation 타입 위치

- **위치**: `shotloom-core` (leading candidate, ADR 는 open question 으로 남김)
- **이유**: normalizer 와 retarget 이 서로 직접 의존하지 않고 core 타입을 매개로 만남. Layering 깔끔.
- **CharacterModel 에는 안 넣음** — character-neutral 계약 위반 (한 anim 이 여러 캐릭터에서 재사용 가능해야 하는데 character 필드로 박으면 1:1 강제)
