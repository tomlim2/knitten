Normalizer Crate Layer

한 문장 요약

shotloom-retarget 안에 섞여있는 정규화 로직을 두 개의 별도 크레이트로 뽑고, 정규화 결과를 CharacterModel 내부에 실어서, 앞으로 A-pose 전환이 와도 retarget/engine/core 시그니처가 흔들리지 않게 만든다.

새 책임 경계
소스 포맷 지식은 normalizer 크레이트 안에만. 바깥 세상은 정규화된 형태만 본다.
CharacterModel 단일 소스
rest pose, foot contact 등이 모델 안에. 다운스트림이 재유도하지 않는다.
retarget는 순수 계산
입력이 canonical 임을 전제. VRM/FBX/PMX 구분 없음.

현재 shotloom-retarget이 소스 포맷 지식까지 떠안고 있는 상태.

문제점
  • retarget 크레이트가 소스 포맷(VRM 본 이름) 지식을 떠안고 있음
  • 정규화 경로가 3군데에 분산 — 각 call site마다 다름
  • foot contact 같은 캐릭터 데이터가 모델이 아니라 retarget 안에 있음
  • FBX/PMX 소스 추가 = adapter 디렉토리 폭증
  • A-pose 전환 = 여러 크레이트에 걸친 refactor

핵심 결정

01

별도 크레이트 2개 (단일 아님)

character 와 animation 은 입력 · 출력 · 변경 주기가 모두 분리. 단일 shotloom-normalize 크레이트로 묶으면 FBX importer 번프가 character 경로를 재빌드.

02

CharacterModel 내장 (#[serde(skip)])

rest_pose 는 런타임 전용. 저장 JSON 형식은 변경 없음. 기존 저장 파일 그대로 역직렬화 가능.

03

RestPose 타입은 shotloom-core

레이어링 방향은 단방향: core ← normalizer ← retarget / engine. core 가 normalizer 에 의존하지 않음.

04

소스 포맷 무관한 CharacterModel

정규화 이후 다운스트림은 VRM 이었는지 FBX 였는지 PMX 였는지 모름. 모든 소스가 한 표현으로 수렴.

05

A-pose 데이터 모델은 지금 안 만듦

CanonicalPoseId enum, per-asset 태그, 버전 캐시 키 — 전부 speculative. A-pose 작업 시작할 때 follow-up ADR 에서 결정.

06

7+ 캐릭터 스폰 floor

설계가 동시 7+ 캐릭터를 깨뜨리면 안 된다. per-char 비용을 현재 수준으로 유지하는 방향. 검증 자체는 별도 follow-up.

  4. 3

RestPose 타입 상세 설계

본 목록 shape, transform 표현, metadata. ADR 수준이 아니라 구현 PR 에서 반복.

rest_pose 디스크 직렬화

지금은 런타임 전용 (#[serde(skip)]). 캐싱 최적화는 별도 추적.

거절된 대안들

A. 정규화를 shotloom-retarget 안에 유지

이미 소스 포맷 adapter, rest-pose reshape, retarget math 가 섞여있음. 새 소스마다 adapter 경로 추가 → 크레이트가 덤프 그라운드화. VRM 하나일 때 나누는 비용이 적고, 나중에 나누는 건 multi-PR refactor.

B. CanonicalPoseId enum + ACTIVE_CANONICAL_POSE const 를 지금 도입

변종이 하나만 inhabited 됨 (CinevArpV1). A-pose 변종 body 는 A-pose math 가 spec 될 때까지 쓸 수 없음. 두 번째 변종 없이 enum 두는 건 "미래 shape 을 광고하는 죽은 코드". per-asset 태그는 캐시 키까지 바꾸게 하고 직렬화 포맷을 오염시킴. A-pose 실제로 올 때 추가.

C. 단일 shotloom-normalize 크레이트 (character / animation 모듈)

character 정규화 (skeleton, foot contact, sole offset) 와 animation 정규화 (keyframe, 본 이름 remap) 는 입력 · 출력 · 변경 주기가 disjoint. 한 크레이트에 묶으면 FBX animation importer 번프가 character 경로를 재빌드. 컴파일 타임 격리 값 있음.

D. CharacterModel 에 직렬화되는 rest pose 필드 추가 (skip 아님)

CharacterModel 은 outliner, inspector, casting, dialog 시스템이 사용. 정규화 런타임 데이터를 serde schema 에 굽으면 그 시스템들이 normalizer 출력 shape 변화에 커플됨 — 이 ADR 이 피하려는 바로 그 커플링. #[serde(skip)] 로 disk 포맷 안정, shape 변경은 바이너리를 탐.

E. CharacterModel 순수 유지, RestPose 별도 전달

retarget facade 가 (&CharacterModel, &RestPose, &NormalizedAnimation) 받고, 모든 다운스트림 caller 가 RestPose 를 CharacterModel 옆에 붙여서 convention 으로 운반. ADR-0029 가 원래 제안했던 구조 — 이 수정판이 명시적으로 뒤집음. 페어를 CharacterModel 안에 두면 caller 코드와 정규화 상태의 커플링 해소.

미래 — A-pose 올 때 뭐가 바뀌나

ADR-0029 의 레이어링 덕분에:

바뀜
normalizer 크레이트 내부

출력 shape 이 ARP 레이아웃 → A-pose 레이아웃 으로 이동.

바뀜
retarget math

새 shape 소비하도록 알고리즘 업데이트. bind-delta 공식 재도출 여부는 그때 판단.

안 바뀜
shotloom-core, shotloom-engine

시그니처 유지. CharacterModel.rest_pose 는 그냥 새 shape 값을 담는다.
