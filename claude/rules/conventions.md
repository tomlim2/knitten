- **Always check repo conventions before non-trivial work.** Before editing code, opening a PR, creating an issue, or making any structural change in a repo, read that repo's conventions IN FULL at the start of the session. Do not rely on memory — conventions drift between sessions.
- **Where to look, in priority order:**
  1. `CONTRIBUTING.md` at repo root — the authoritative contributor guide, often lists co-location checklists, MAP.md update rules, and required follow-up artifacts for new modules.
  2. `AGENTS.md` at repo root — agent-facing workflow, ownership model, breadcrumb doc requirements.
  3. `docs/guidelines/` directory — `pr-guideline.md`, `commit-guideline.md`, `code-review-guideline.md`, `review-rust.md` / `review-typescript.md` etc. These are the review criteria your PR will be judged against.
  4. `docs/adr/` — architecture decisions that bind design choices (scope boundaries, crate layering, dependency policies).
  5. Repo-local Claude rule files — `~/.claude/rules/<repo>-git.md` (e.g. `shotloom-git.md`), which **override** the generic rules in this folder when they conflict.
- **Re-read every session.** Even if you "already read it last week" — guidelines get updated, ADRs get added, and stale memory causes CHANGES_REQUESTED. A 2-minute re-read is cheaper than a 2-hour rework.
- **Before opening a PR, audit the branch against the guideline.** Spawn a sub-agent (or run through yourself) to verify: commit format, PR body shape, required sections, co-location artifacts (MAP.md, breadcrumb READMEs, ADR index updates), new-dep justifications, test coverage, `#[allow(...)]` comments, `unwrap()`/`expect()` in non-test paths. If the repo has a `code-review-guideline.md`, treat every P0/P1 item as a pre-PR gate.
- **Always re-check conventions when reviewing code (your own or someone else's).** At the start of every review session, re-read `code-review-guideline.md`, `review-rust.md` (or the relevant language review file), and `pr-guideline.md` before forming any review comments. This applies to: self-review before push, responding to a reviewer's feedback, reviewing a sub-agent's output, and reviewing someone else's PR. Do not skip this even if you "just read it an hour ago" — the guideline is the single source of truth for what counts as a defect, and any review comment that conflicts with the guideline wastes the author's time.
- **Repo-specific rule files take precedence.** When `shotloom-git.md` says one thing and generic `git.md` says another, the repo-specific file wins for that repo.
- **When you discover a new convention, update the relevant Claude rule file.** If a shotloom guideline surprises you, add it to `rules/shotloom-git.md` (or the appropriate repo-specific rule) so the next session doesn't miss it.
- **Guideline trumps habit.** When a rule you've been following in one project doesn't apply to another, follow the other project's rule, not the one you're used to.
