# 2026-04-10: arp2vrm-score 설계

FK 스코어링이 LLM 토큰을 너무 많이 잡아먹는 문제를 풀기 위해 Codex + Opus 병렬 의견 받고, 검증 범위를 ARP→VRM 리타게터로 좁힘. 모드 분리 + LLM gate 도입 결정.

---

## 문제

현재 FK 스코어링은 LLM 호출 시 입력 컨텍스트가 너무 무겁다.

- 본 100+개 raw error 데이터
- ARP↔VRM 매핑 테이블 매번 전송
- 레퍼런스 포즈 데이터
- 복수 시스템 (FK RMS, visual audit, finger curl)이 한 흐름에 섞여있음

병목은 **결과값 읽기**가 아니라 **입력**.

---

## Codex 의견 요약

1. Rust에서 집계 후 요약만 전달 — 부위별 max/p95/mean + 초과 본 top N
2. LLM은 점수 계산 금지, 1차 판정은 Rust threshold/weighted score, LLM은 예외 판정만
3. 매핑/레퍼런스는 ID화 (`mapping=arp_vrm_std_03`) — 매번 보내지 않음

## Opus 의견 요약

1. 단일 진입점 CLI — 한 줄 출력으로 압축
2. PASS면 LLM 호출 자체를 없앰 (토큰 0)
3. 판단은 Rust threshold가 진실, LLM은 추론(원인 가설, 코드 위치 추천)만

## 합의점

- Rust가 판정, LLM은 추론
- 요약/집계만 전달
- 레퍼런스/매핑은 ID 참조

## 결정 사항

### 1. 검증 범위 축소: ARP → VRM Retargeter

다루는 것:

- Blender ARP FBX → VRM 휴머노이드 본 리타게팅 정확도

다루지 않는 것:

- Visual audit (스크린샷)
- IBM/skinning 검증
- Spring bone, MToon

### 2. 모드 분리 (`verify` vs `score`)

| 모드 | 목적 | 출력 | LLM |
|------|------|------|-----|
| `verify` | 게이트 (PASS/FAIL) | 한 줄 | PASS면 0, FAIL이면 hint |
| `score` | 개선 추적 (delta) | 부위별 + last run 비교 | grade B 미만일 때만 |

### 3. 본 범위 추가 분리 (모드)

VRM Humanoid 본은 손가락까지 포함해 54개. 알고리즘이 다르므로 모드로 나눈다.

- `arp2vrm-score body` — 코어 휴머노이드 (24개: required 15 + optional body 9)
- `arp2vrm-score fingers` — 손가락만 (30개)
- `arp2vrm-score full` — 전체 (54개)

근거: 손가락은 finger curl pipeline에서 별도 알고리즘 사용 중. 합치면 threshold/가중치가 섞여 신호 품질이 떨어짐.

자세한 본 테이블은 [[learning-vrm-humanoid-bones]] 참고.

### 4. LLM 호출 정책

- Grade A/B → silent pass, LLM 호출 없음
- Grade C/F → JSON payload로 LLM에 전달
- payload 내용: overall RMS, 부위별 집계, top N 회귀 본, last run delta, hint

### 5. History 저장 — 저장만, 비교는 opt-in

매 run 결과를 `bevy-vrm/scoring-history/` (gitignored)에 JSON으로 저장. **저장은 공짜(디스크)지만 LLM에 보내면 토큰이므로 비교는 opt-in.**

- 기본: 저장만 하고 비교 안 함
- `score --vs-last`: 명시적으로 요청할 때만 직전 run과 diff
- 자동 추세 추론은 회귀 의심 시에만 수동 호출

### 6. 본 가중치 — 부위별 weighted

루트 본 에러는 캐릭터 전체에 영향, 손목은 국소적이므로 가중치 적용:

- `hips` × 3
- `spine`, `chest` × 2
- `arms`, `legs` × 1
- `hands`, `feet`, `head` × 1

근거: 신호 품질 우선. 균등 RMS는 hips 0.1m와 손목 0.1m를 같게 보지만, 실제로는 전자가 훨씬 치명적.

### 7. 검증/회귀 목표 등급

A(0.02m)는 비현실적, **B(0.05m)를 실용 목표**로 설정. 현재 standing은 0.067m=C, B 도달이 다음 마일스톤.

## 토큰 경제 (예상)

### 호출당 토큰

| 시나리오 | 현재 | arp2vrm-score | 절감률 |
|----------|------|---------------|--------|
| 검증 통과 (`verify` PASS) | ~3,000 | ~10 (한 줄) | **99.7%** |
| 검증 실패 (`verify` FAIL) | ~3,000 | ~200 (요약+hint) | **93%** |
| 점수 확인 (`score`) | ~3,000 | ~400 (부위 집계) | **87%** |
| 점수+델타 (`score --vs-last`) | ~3,500 | ~800 (델타 포함) | **77%** |

### 일일 절감 (활발한 개발일 가정)

가정: verify 25회 (대부분 PASS), score 5회

| 항목 | 현재 | arp2vrm-score |
|------|------|---------------|
| verify × 25 | 75,000 | 23 PASS×10 + 2 FAIL×200 = **630** |
| score × 5 | 15,000 | 5×400 = **2,000** |
| **합계/일** | **90,000** | **2,630** |
| **절감** | — | **~97%** |

### 핵심 효과

가장 큰 절감은 **PASS 케이스가 토큰을 거의 안 먹는다**는 것. 현재는 매 검증마다 3,000 토큰이 나가지만, 새 설계에서는 PASS는 10 토큰 (사실상 0). 개발 중 90%가 PASS라고 보면 이게 절감의 대부분을 차지.

### 부수 효과 (수치화 어려움)

- **컨텍스트 윈도우 보존** — 한 세션에서 verify를 여러 번 돌려도 컨텍스트가 안 채워짐 → 더 긴 작업 가능
- **신호 품질 향상** — 100+ 본 raw에서 LLM이 노이즈에 휘말리던 게 사라짐. 부위별 집계 + worst N만 보면 판단이 더 일관됨
- **CI 비용 0** — 빌드 게이트로 verify 쓰면 LLM 호출 자체가 없으므로 CI 비용 무관

## 저녁 후반 — Finger 파이프라인 조사 → ARP-VRM 어댑터 아키텍처 결정

손가락 파이프라인 작업을 다음 단계로 시작했는데, 예상 못한 큰 아키텍처 발견이 나옴. 세션 최대 산출물 중 하나.

### 시작점 — 스크린샷 하나

유저가 F8 preset(standing FBX + male VRM) 뷰어 띄우고 스크린샷 공유. 주황(FBX) 손은 자연스러운 standing 손 모양, 마젠타(VRM) 손은 손가락이 팔 축 따라 일자로 뻗음. "이거 사겠나요?" — 반품 수준 퀄리티.

### 네 번의 잘못된 진단 (세션 기록)

실측 데이터 이전에 제가 내린 잘못된 판정 4회:

1. ~~"공식이 chain curl을 cancel out"~~ — 수학적으로 틀림. 부모의 anim_rot이 자식 공식에 들어가지 않음
2. ~~"80-90% 손실"~~ — metric 혼동 (rest-magnitude vs frame-to-frame velocity)
3. ~~"absolute mapping 필요"~~ — FBX raw peak 15.8° = 리타게터 output 15.8°, 0% loss 로 기각
4. ~~"로더 버그"~~ — `dump-vrm-transforms` CLI 로 byte-match 확인, 로더 무고

매번 "CLI 숫자는 OK 같은데 뷰어는 왜 다를까" 에서 잘못된 결론으로 점프. **숫자 먼저, 해석 나중** 원칙 반복 학습.

### 진짜 원인 — 두 rig 의 "0 지점" 불일치

FBX 가 데이터 저장하는 방식:
- **Rest pose**: 노드 `PreRotation × Lcl_Rotation 기본값` (별도 저장)
- **Animation**: AnimationCurve 에 **절대값** 리스트 (델타 아님)
- 델타는 mapping.rs 가 `rest_inv × absolute` 로 파생

ARP 와 VRM 의 rest pose 자체가 다름:
- ARP 손가락 rest: 살짝 curl 된 "relaxed hand" (Blender ARP 기본)
- VRM 손가락 rest: 쫙 폄 "straight" (VRoid 기본, ≈ identity)

두 rig 모두 자기 rest 를 "0 지점" 으로 잡음. Standing 애니메이션은 ARP 기준 delta ≈ 0 (이미 rest 에 가까움). 그래서:

```
ARP  : ARP_rest (curl)    + delta(0) = curl      → 주황 자연스러움 ✅
VRM  : VRM_rest (straight) + delta(0) = straight → 마젠타 일자 ❌
```

Body 본은 delta 가 커서(T-pose→standing) rest 불일치가 묻혀 시각적으로 OK 로 보였지만, finger 는 delta 가 작아서 불일치가 그대로 드러남.

### 유저가 찾은 해결책 — ARP-VRM 어댑터

유저 제안: **"로드된 VRM 을 ARP rest 처럼 굽히고, 그 상태를 새 rest 로 설정한 다음 일반 retargeter 로 델타 적용"**

이건 absolute mapping(기각한 것) 과 다름:

| | Absolute mapping (기각) | Rest alignment (채택) |
|---|---|---|
| 적용 시점 | 매 프레임 | init 1회 |
| 공식 변경 | 본 종류별 분기 | 공식 그대로 |
| body/finger 코드 | 분리 | 통일 |
| delta 의미 | 사라짐 | 그대로 유지 |
| 원복 | 어려움 | 쉬움 |

유저의 또 다른 관찰 "축도 똑같잖아요" — `normalize_vrm_bones_180y` 후 VRM 과 Blender FBX 가 같은 Y-up 좌표계. `coord_rot = identity` 이면 정렬 수식이 극단적으로 단순:

```rust
dst_rest_local_new[finger] = src_rest[finger]  // 직접 복사
```

단 bone-internal 축 (본 길이 방향) 이 동일한지는 실측 검증 필요.

### 아키텍처 전환 — 어댑터 레이어 개념

이게 "리타게터 공식 수정" 이 아니라 **ARP↔VRM 전용 어댑터 레이어 신설**. 일반 retargeter 는 불변, 알려진 소스(ARP)→알려진 타겟(VRM) 경로에만 적용되는 별도 모듈.

제안 구조:

```
crates/cinev_retarget/src/
├── retargeter.rs          ← 일반 공식 (불변)
├── mapping.rs             ← FBX 파싱 (불변)
├── vrm_rest.rs            ← VRM 파싱 (불변)
└── adapters/               ← ★ 신규 ★
    ├── mod.rs
    └── arp_vrm.rs         ← ARP rest → VRM rest 정렬 로직
```

이건 `project_arp_retarget_redesign` 메모리의 첫 조각. "ARP retarget crate 전체 redesign" 이 막연히 큰 작업이었는데, **어댑터 모듈 하나 추가** 로 재구성 경로가 보임.

### 구체적 책임 분리 (adapters/arp_vrm.rs)

1. **Detect**: FBX 가 ARP 인지 판별 (source_type + 본 명명 패턴)
2. **Align rest**: finger 본의 `dst_rest_local` 을 `src_rest` 로 override
3. **Propagate**: 자식 본의 global rest 재계산 (chain consistency)
4. **Validate**: anatomically valid 한지 체크
5. **Revert**: feature flag off 면 아무 것도 안 함

- **"리타게터 버그" 보다 "아키텍처 경계" 로 생각**. ARP 만 특이한 rest 를 가진 게 문제지 공식이 틀린 게 아님
- **유저가 세 번이나 방향 바로잡음** — "공식 수정" 에서 길 잃은 나를 "어댑터 레이어" 로 끌어냄. 컨트롤타워가 조종 못하는 시점에 유저 판단이 더 정확
