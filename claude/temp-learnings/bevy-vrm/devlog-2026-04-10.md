# 2026-04-10: arp2vrm-score 설계

FK 스코어링이 LLM 토큰을 너무 많이 잡아먹는 문제를 풀기 위해 Codex + Opus 병렬 의견 받고, 검증 범위를 ARP→VRM 리타게터로 좁힘. 모드 분리 + LLM gate 도입 결정.

---

## 문제

현재 FK 스코어링은 LLM 호출 시 입력 컨텍스트가 너무 무겁다.

- 본 100+개 raw error 데이터
- ARP↔VRM 매핑 테이블 매번 전송
- 레퍼런스 포즈 데이터
- 복수 시스템 (FK RMS, visual audit, finger curl)이 한 흐름에 섞여있음

병목은 **결과값 읽기**가 아니라 **입력**.

---

## Codex 의견 요약

1. Rust에서 집계 후 요약만 전달 — 부위별 max/p95/mean + 초과 본 top N
2. LLM은 점수 계산 금지, 1차 판정은 Rust threshold/weighted score, LLM은 예외 판정만
3. 매핑/레퍼런스는 ID화 (`mapping=arp_vrm_std_03`) — 매번 보내지 않음

## Opus 의견 요약

1. 단일 진입점 CLI — 한 줄 출력으로 압축
2. PASS면 LLM 호출 자체를 없앰 (토큰 0)
3. 판단은 Rust threshold가 진실, LLM은 추론(원인 가설, 코드 위치 추천)만

## 합의점

- Rust가 판정, LLM은 추론
- 요약/집계만 전달
- 레퍼런스/매핑은 ID 참조

---

## 결정 사항

### 1. 검증 범위 축소: ARP → VRM Retargeter

다루는 것:

- Blender ARP FBX → VRM 휴머노이드 본 리타게팅 정확도

다루지 않는 것:

- Visual audit (스크린샷)
- IBM/skinning 검증
- Spring bone, MToon

### 2. 모드 분리 (`verify` vs `score`)

| 모드 | 목적 | 출력 | LLM |
|------|------|------|-----|
| `verify` | 게이트 (PASS/FAIL) | 한 줄 | PASS면 0, FAIL이면 hint |
| `score` | 개선 추적 (delta) | 부위별 + last run 비교 | grade B 미만일 때만 |

### 3. 본 범위 추가 분리 (모드)

VRM Humanoid 본은 손가락까지 포함해 54개. 알고리즘이 다르므로 모드로 나눈다.

- `arp2vrm-score body` — 코어 휴머노이드 (24개: required 15 + optional body 9)
- `arp2vrm-score fingers` — 손가락만 (30개)
- `arp2vrm-score full` — 전체 (54개)

근거: 손가락은 finger curl pipeline에서 별도 알고리즘 사용 중. 합치면 threshold/가중치가 섞여 신호 품질이 떨어짐.

자세한 본 테이블은 [[learning-vrm-humanoid-bones]] 참고.

### 4. LLM 호출 정책

- Grade A/B → silent pass, LLM 호출 없음
- Grade C/F → JSON payload로 LLM에 전달
- payload 내용: overall RMS, 부위별 집계, top N 회귀 본, last run delta, hint

### 5. History 저장 — 저장만, 비교는 opt-in

매 run 결과를 `bevy-vrm/scoring-history/` (gitignored)에 JSON으로 저장. **저장은 공짜(디스크)지만 LLM에 보내면 토큰이므로 비교는 opt-in.**

- 기본: 저장만 하고 비교 안 함
- `score --vs-last`: 명시적으로 요청할 때만 직전 run과 diff
- 자동 추세 추론은 회귀 의심 시에만 수동 호출

### 6. 본 가중치 — 부위별 weighted

루트 본 에러는 캐릭터 전체에 영향, 손목은 국소적이므로 가중치 적용:

- `hips` × 3
- `spine`, `chest` × 2
- `arms`, `legs` × 1
- `hands`, `feet`, `head` × 1

근거: 신호 품질 우선. 균등 RMS는 hips 0.1m와 손목 0.1m를 같게 보지만, 실제로는 전자가 훨씬 치명적.

### 7. 검증/회귀 목표 등급

A(0.02m)는 비현실적, **B(0.05m)를 실용 목표**로 설정. 현재 standing은 0.067m=C, B 도달이 다음 마일스톤.

## 토큰 경제 (예상)

### 호출당 토큰

| 시나리오 | 현재 | arp2vrm-score | 절감률 |
|----------|------|---------------|--------|
| 검증 통과 (`verify` PASS) | ~3,000 | ~10 (한 줄) | **99.7%** |
| 검증 실패 (`verify` FAIL) | ~3,000 | ~200 (요약+hint) | **93%** |
| 점수 확인 (`score`) | ~3,000 | ~400 (부위 집계) | **87%** |
| 점수+델타 (`score --vs-last`) | ~3,500 | ~800 (델타 포함) | **77%** |

### 일일 절감 (활발한 개발일 가정)

가정: verify 25회 (대부분 PASS), score 5회

| 항목 | 현재 | arp2vrm-score |
|------|------|---------------|
| verify × 25 | 75,000 | 23 PASS×10 + 2 FAIL×200 = **630** |
| score × 5 | 15,000 | 5×400 = **2,000** |
| **합계/일** | **90,000** | **2,630** |
| **절감** | — | **~97%** |

### 핵심 효과

가장 큰 절감은 **PASS 케이스가 토큰을 거의 안 먹는다**는 것. 현재는 매 검증마다 3,000 토큰이 나가지만, 새 설계에서는 PASS는 10 토큰 (사실상 0). 개발 중 90%가 PASS라고 보면 이게 절감의 대부분을 차지.

### 부수 효과 (수치화 어려움)

- **컨텍스트 윈도우 보존** — 한 세션에서 verify를 여러 번 돌려도 컨텍스트가 안 채워짐 → 더 긴 작업 가능
- **신호 품질 향상** — 100+ 본 raw에서 LLM이 노이즈에 휘말리던 게 사라짐. 부위별 집계 + worst N만 보면 판단이 더 일관됨
- **CI 비용 0** — 빌드 게이트로 verify 쓰면 LLM 호출 자체가 없으므로 CI 비용 무관

## 새로 알게 된 것

- VRM Humanoid는 손가락 포함 54개 본 (Required 15 + Optional Body 9 + Fingers 30)
- VRM 0.x → 1.0에서 엄지 본 이름이 한 칸 밀림 (Proximal → Metacarpal)
- Bevy 생태계엔 ARP→VRM 리타게터가 없음 (직접 만들어야 함)

## 해소된 것

- History → bevy-vrm 레포 안 `scoring-history/` (gitignored), 저장만
- 본 가중치 → 부위별 weighted (hips×3, spine/chest×2, 나머지×1)
- 비교 → 기본 OFF, `--vs-last` 플래그로 opt-in (토큰 절약)
- FAIL payload → 텍스트 (가벼운 쪽)
- fingers 모드 → 설계 중, 현재는 body에만 집중
- 회사 ARP 전환 → 가능성 있음, 합치면 그래픽 엔지니어 정체성 강화
- 목표 등급 → A는 비현실, **B를 실용 목표**

## 여전히 불명확

- **부위 가중치 수치**: hips×3가 적절한지, ×5나 ×2가 나은지는 구현 후 튜닝 필요
- **B 도달 전략**: 현재 0.067m → 0.05m로 가려면 가장 큰 에러 본부터? 아니면 루트(hips)부터?
