# Bootstrap (부트스트랩)

**Date:** 2026-04-14

## 핵심

**부트스트랩 = "내용 없는 빈 골격이지만 시스템 안에서 굴러가는 상태".**

어원: 자기 부츠 끈을 잡아당겨 자기를 들어올린다는 비유 → "아무것도
없는 상태에서 시동 걸기".

## 비슷한 단어와의 차이 (중요)

| 단어 | 핵심 |
|---|---|
| **draft (초안)** | 내용은 있는데 미완성. 다듬기 전 1차본. |
| **bootstrap (부트스트랩)** | 내용은 거의 없고, 시동만 걸리는 최소 셋업. |
| **scaffold (스캐폴드)** | 비계 — 빈 폴더/파일 구조. 부트스트랩과 거의 동의어. |
| **prototype (프로토타입)** | 핵심 기능 1개를 빠르게 검증하는 시제품. |

**핵심 구분**: 부트스트랩의 본질은 "내용"이 아니라 **"연결"**.
코드 0줄이어도 됨. 중요한 건:
- workspace/시스템에 등록됨 ✅
- 빌드 도구가 인식함 ✅
- 빌드 통과 ✅
- CI 돎 ✅

이 4가지가 되면 부트스트랩 완료.

## 비유

- **초안** = 원고 1차본 (글은 있는데 거칠다)
- **부트스트랩** = 새 책의 빈 표지 + 목차 자리 + ISBN 등록
  (책장에 꽂힐 자리는 만들어짐, 내용은 0쪽)

## 분야별 의미

| 맥락 | 뜻 |
|---|---|
| **OS** | 부트로더 (BIOS → 커널 시동) |
| **언어/컴파일러** | 자기 자신으로 자기를 컴파일 (Rust 컴파일러가 Rust로 작성됨) |
| **프로젝트 시작** | `npm init`, `cargo new` — 빈 골격 |
| **통계** | bootstrap sampling — 데이터 재추출 (다른 의미) |
| **CSS 프레임워크** | Bootstrap (이름이 그래서 그럼) |

## 실제 예 — shotloom-retarget 부트스트랩

```rust
// crates/shotloom-retarget/src/lib.rs
//! Retarget pipeline for shotloom (placeholder).

#[cfg(test)]
mod tests {
    #[test]
    fn it_compiles() {
        assert_eq!(2 + 2, 4);
    }
}
```

진짜로 이게 다. 코드 0줄에 가까움. 그래도 **"crate가 존재하고 빌드되고
테스트가 도는" 상태**가 만들어진 것.

## 왜 부트스트랩 단계를 따로 두는가

코드 옮기기 전에 빈 그릇을 먼저 만드는 게 정석. 이유:

1. **빌드 시스템 정합성 먼저 검증** — 의존성 충돌 없는지 코드 옮기기 전에 확인
2. **placeholder 한 줄로 컴파일 OK 만들기** — 다음 단계부터 "기능 추가"에만 집중
3. **CI 파이프라인 확인** — 새 crate가 CI에 자동 포함되는지
4. **작은 PR로 분리** — 부트스트랩은 코드 0줄, 그다음 PR이 진짜 코드.
   리뷰 부담 ↓

= **"Start small, prove, then grow"** 원칙과 정확히 같은 발상.
빈 crate라도 한 번 빌드 통과 → prove → 그다음에 코드 채우기.

## shotloom 이식 시퀀스 예

1. ✅ **Bootstrap** — 빈 crate
2. **타입 정의 이식** — `RetargetConfig`, `RetargetResult` 등 contract surface만
3. **lib 본체 이식** — `retargeter.rs`, 3-pass 로직
4. **adapters 이식** — `arp_vrm.rs` 등
5. **quality/rubric 이식** — A/B/C 평가
6. **shotloom-engine과 연결** — 실제 호출

각 단계가 독립 PR. 부트스트랩이 그 첫 단추.

## 한 줄

**Bootstrap = "굴러가는 빈 골격".** 초안과 다른 점은 *내용 유무*가
아니라 *시스템 통합 여부*. 다음 단계가 진짜 알맹이 채우기.
