# Shotloom devlog 2026-05-18

## PR 349

1. 지적 — derived target-id set의 불가능한 rollback branch는 invariant로
   고정해야 한다. 리뷰는 `clear_background_props`가 `shot.props`에서 제거
   대상 prop id를 모은 뒤 같은 exclusive borrow 안에서 제거하므로
   `PropNotFound` rollback path가 실제로는 도달 불가능하다고 봤다. 이 원칙이
   맞는 이유는 error code surface가 contract에 없는 실패를 새로 만들지
   않도록 하기 위해서다. → `489821fe`에서 clear path가 derived target id
   set을 infallible set으로 다루고, 제거 전에 invariant comment를 남겼다.

2. 지적 — conditional selection event는 negative overlap case로 검증한다.
   리뷰는 background props가 제거되지만 selection과 겹치지 않는 경우가
   테스트되지 않았다고 봤다. 조건부 event contract는 happy path와 no-op만으로
   충분하지 않다. → `489821fe`에서 background props 두 개를 제거하되 selection
   overlap이 없는 regression을 추가했고, `PropRemoved` 두 건, no
   `SelectionChanged`, `BundleChanged` 순서를 검증했다.

3. 지적 — mirror event는 command acknowledgement처럼 보이면 안 된다.
   리뷰는 coalesced `shot_loaded` mirror가 존재한다는 것만으로는 부족하고,
   `caused_by_command_id`가 없음을 pin해야 한다고 지적했다. 호출자가 no-op
   판별에 mirror event를 쓰면 clear command contract가 흔들린다. →
   `489821fe`에서 clear happy-path test가 mirror `ShotLoaded`의 command
   correlation absence를 검증하게 됐다.

## PR 350

1. 지적 — dead branch cleanup도 삭제된 branch의 fallthrough 의미를 pin한다.
   리뷰는 public API가 현재 `VrmVersion::V1_0`만 쓰더라도, 제거된 default
   override table에는 `0.x` branch도 있었으니 fallthrough 결과를 명시적으로
   검증하라고 했다. 삭제가 안전하다는 말은 "도달하지 않음"과 "도달해도
   canonical direct map으로 수렴함"을 구분해야 한다. → `fa5b567d`에서 default
   config test가 `1.0`과 `0.x` version key를 모두 확인하게 됐다.

2. 지적 — empty override table은 code site에서도 이유가 보여야 한다. 리뷰는
   `Default::default()`가 empty map이라는 사실과 그 의미를 읽으려면 다른 파일로
   점프해야 한다고 봤다. README가 rationale을 설명해도, config construction
   site에는 built-in path가 `direct_map`을 의도적으로 신뢰한다는 anchor가
   필요하다. → `fa5b567d`에서 empty default override table 옆에 direct-map
   reliance comment를 추가했다.

3. 지적 — retained branch 문서는 코드 용어와 responsibility split을 따라야
   한다. 리뷰는 "thumb CMC algorithm" 표현이 코드베이스의
   "carpometacarpal coupling" 표현과 어긋나고, toe-less guard와 foot-contact
   consumption을 같은 fallback으로 묶는 것도 부정확하다고 봤다. → `fa5b567d`
   에서 README가 carpometacarpal-coupling 용어와 finger-axis module anchor를
   쓰고, toe-less guard와 foot-contact consumption을 분리했다.

## PR 351

   스타일을 써야 한다. 리뷰는 `thiserror`만 bare name이 되고 `serde = "1"`은
   남아 있어 mixed style처럼 읽힌다고 봤다. dependency version ownership이
   workspace root로 이동하면 crate README는 version pin을 반복하지 않는 편이
   맞다. → `a7221ae4`에서 FBX animation README가 `serde`도 bare dependency
   name으로 쓰게 됐다.

2. 지적 — tech-debt cleanup guidance는 dependency ownership 이동 뒤 stale해진다.
   리뷰는 `thiserror`가 이제 root workspace dependency인데, 기존 문서가
   asset-pipeline crates를 통해 이미 있다고 설명한다고 봤다. cleanup 문서는
   앞으로 적용할 idiom을 가리켜야 하므로 stale wording이 남으면 다음 작업자가
   같은 manifest drift를 반복할 수 있다. → `a7221ae4`에서 manual error typing
   cleanup guidance가 `thiserror = { workspace = true }`를 쓰고 root workspace
   manifest가 version을 소유한다고 설명하게 됐다.

## PR 352

1. 지적 — ADR Decision은 durable claim만 소유하고 catalogue detail은 spec으로
   보낸다. 리뷰는 ADR이 role-vs-representation split이라는 핵심 결정과 함께
   `StageElement`/`StageRenderable` carrier 이름, role membership,
   representation membership을 같이 열거한다고 지적했다. ADR은 rename-safe한
   architectural decision을 남기는 문서이고, vocabulary membership과 예시는
   owning spec이 맡아야 drift가 나지 않는다. → `a6f33439`에서 ADR Decision은
   role과 representation이 independent axes라는 claim만 남기고, membership과
   definitions는 spec으로 위임했다.

2. 지적 — 현재 코드 surface 이름은 ADR의 primary subject가 아니면 쓰지 않는다.
   리뷰는 `StageEnvironment`, `StageRequest`, `spawn_background_props` 같은
   current compatibility names가 ADR에 직접 들어가면 rename-fragile하다고
   봤다. Stage entity decision이 기록해야 하는 것은 "기존 stage-related
   runtime surfaces는 compatibility path로 남는다"는 durable claim이지,
   지금의 symbol inventory가 아니다. → `a6f33439`에서 ADR은 generic
   compatibility-path language로 바뀌고 current membership은 `MAP.md`와 owning
   crate docs가 소유하게 됐다.

3. 지적 — runtime topology와 system shape는 spec이 아니라 architecture doc에
   둔다. 리뷰는 spec의 Runtime Hydration 섹션이 Stage root, child entities,
   Bevy systems, optional runtime components를 설명하므로 product behavior
   spec이 아니라 architecture/module-boundary content라고 봤다. AFDS routing상
   specs는 durable behavior와 terminology를 맡고, runtime topology는
   `docs/arch/`나 module docs가 맡는 것이 맞다. → `a6f33439`에서 runtime
   topology는 `docs/arch/stage-runtime-topology.md`로 이동하고, spec에는
   persisted authoring과 runtime regeneration invariant만 남았다.

4. 지적 — conceptual shape와 authoring operations는 field sketch나 recipe가
   아니라 invariant로 써야 한다. 리뷰는 spec 안의 nested field listings,
   create/promote operation rows, asset metadata JSON sketch가 구현 모양처럼
   읽힌다고 지적했다. 명세가 아직 구현되지 않은 field shape를 보여주면 나중에
   schema와 implementation이 달라질 때 stale contract가 된다. → `a6f33439`에서
   conceptual sketch는 ownership groups와 relationships로 바뀌고, operation
   rows는 postcondition/invariant 중심으로 재작성됐으며, asset catalog JSON
   shape는 prose hint contract로 대체됐다.

> [!abstract] Rule
> ADR은 durable decision을 소유하고, spec은 vocabulary membership과 product
> behavior를 소유하며, architecture doc은 runtime topology와 system shape를
> 소유한다. 한 문서가 다른 문서의 catalogue를 반복하면 다음 rename에서 바로
> stale해진다. #rule

> [!tip] event contract tests
> Command handler test는 event가 "있다"뿐 아니라 correlation, absence, ordering
> 중 contract가 의존하는 축을 따로 pin해야 한다.

> [!warning] cleanup PRs
> 삭제 PR은 제거 대상이 dead였다는 사실만 증명하면 부족하다. 삭제 뒤 남는
> fallback path가 canonical behavior로 수렴한다는 regression도 같이 필요하다.
